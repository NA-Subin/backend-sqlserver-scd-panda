ภาพรวมระบบ และรุ่นนี้ต่างจากรุ่น PostgreSQL ตรงไหน

ระบบ PandaStar Oil มี backend ให้เลือก 2 รุ่นที่ทำหน้าที่เหมือนกันทุกอย่าง ต่างกันแค่โปรแกรมฐานข้อมูลที่ใช้เก็บข้อมูล เอกสารนี้เขียนสำหรับรุ่น SQL Server โดยเฉพาะ — ถ้าเซิร์ฟเวอร์จริงของคุณใช้ PostgreSQL อยู่แล้ว ให้ใช้คู่มือของ repo backend-scd-panda แทน (มีคู่มือแยกอยู่ในนั้นเหมือนกัน)

ระบบนี้ประกอบด้วยอะไรบ้าง

🖥️

Frontend

หน้าเว็บที่พนักงาน/ผู้ใช้เห็นและกดใช้งานจริง เหมือน "หน้าร้าน" — ตัวมันเองไม่เก็บข้อมูลอะไร แค่ไปขอข้อมูลจาก backend มาแสดง

⚙️

Backend

ตัวกลางที่รับคำขอจากหน้าเว็บ ไปอ่าน/เขียนฐานข้อมูลให้ เหมือน "พนักงานหลังร้าน" ที่วิ่งเข้าคลังไปหยิบของมาให้ลูกค้าหน้าร้าน

🗄️

ฐานข้อมูล (SQL Server)

ที่เก็บข้อมูลจริงทั้งหมดของบริษัท เช่น รายชื่อพนักงาน รถ ลูกค้า ใบเสร็จ เหมือน "คลังสินค้า" ที่เก็บของจริงไว้ข้างใน

สิ่งสำคัญที่สุดที่ต้องเข้าใจก่อนเริ่ม: repo ทั้ง 2 อันบน GitHub (backend-sqlserver-scd-panda, frontend-scd-panda) มีแค่ "พิมพ์เขียว" ของระบบ คือตัวโปรแกรมเปล่า ๆ — ไม่มีข้อมูลจริงของบริษัทติดไปด้วยเลยแม้แต่แถวเดียว เหมือนได้แบบแปลนบ้านมา แต่ยังไม่มีของในบ้าน ต้องมีไฟล์ข้อมูลจริงอีกไฟล์หนึ่งแยกต่างหาก (Firebase export หรือไฟล์สำรอง .bak จากระบบที่ใช้อยู่แล้ว) มาเติมเข้าไป — ดูรายการที่ต้องขอด้านล่าง

ทำไมต้องมีรุ่น SQL Server แยกจากรุ่น PostgreSQL

เซิร์ฟเวอร์จริงบางแห่งกำหนดให้ใช้ SQL Server เป็นมาตรฐานอยู่แล้ว รุ่นนี้จึงถูกสร้างขึ้นให้ทำงานแบบเดียวกับรุ่น PostgreSQL ทุกประการ (CRUD, ล็อกอิน, รายงานปั๊มน้ำมัน, นำเข้าข้อมูล, สำรองข้อมูล) เพียงแต่พูดคุยกับ SQL Server แทน Postgres เบื้องหลัง — โค้ดฝั่ง frontend เป็นไฟล์เดียวกันเป๊ะกับรุ่น Postgres ต่างกันแค่ตั้งค่าให้ชี้ไปที่ backend คนละตัว

ติดตั้ง SQL Server บนเครื่องเปล่า

ข้ามขั้นตอนนี้ทั้งหมดได้ถ้าเครื่องมี SQL Server ที่พร้อมใช้งานอยู่แล้ว (เช่น DBA เตรียมไว้ให้แยกต่างหาก) — ข้ามไปขั้นตอนที่ 4 ได้เลย ถ้ายังไม่มีให้ทำตามนี้

ดาวน์โหลดตัวติดตั้ง

ไปที่หน้าเว็บทางการ SQL Server Downloads ของ Microsoft แล้วเลือก edition Developer (ฟรี ฟีเจอร์ครบเหมือน Enterprise เหมาะกับใช้งานจริงในองค์กรที่ไม่ได้ขายต่อ Microsoft SQL Server เป็นสินค้า) จะได้ไฟล์ bootstrapper ขนาดเล็ก (SQLServer-Dev-SSEI.exe ประมาณ 5 MB)

ติดตั้งแบบ 2 ขั้นตอน (แนะนำ — ควบคุมได้ทุกจุด)

bootstrapper ตัวเล็กบางครั้งไม่รองรับการติดตั้งแบบ unattended เต็มรูปแบบในคำสั่งเดียว แยกเป็น 2 ขั้นเชื่อถือได้กว่า:

# ขั้นที่ 1 — ดาวน์โหลด media เต็ม (ไม่ต้องเป็น Administrator)
SQLServer-Dev-SSEI.exe /ACTION=Download /MEDIATYPE=CAB /QUIETSIMPLE /IACCEPTSQLSERVERLICENSETERMS

# ขั้นที่ 2 — ติดตั้งจริง (ต้องเปิด PowerShell แบบ "Run as Administrator")
<path-to-media>\setup.exe /ACTION=Install /QUIET /IACCEPTSQLSERVERLICENSETERMS `
  /FEATURES=SQLEngine `
  /INSTANCENAME=MSSQLSERVER `
  /SECURITYMODE=SQL /SAPWD="ตั้งรหัสผ่าน sa ที่นี่" `
  /SQLSYSADMINACCOUNTS="BUILTIN\Administrators" `
  /TCPENABLED=1
3 จุดที่พลาดบ่อยที่สุดตอนติดตั้ง:
  1. /SECURITYMODE=SQL ต้องระบุเสมอ — ไม่งั้นจะได้ Windows Authentication อย่างเดียว ต่อด้วย user/password (SQL auth) ไม่ได้เลย ซึ่งเป็นวิธีที่ backend ตัวนี้ต่อฐานข้อมูล
  2. /TCPENABLED=1 ต้องระบุเสมอ — ค่าเริ่มต้นของ SQL Server ปิด TCP/IP protocol ไว้ ถ้าลืมข้อนี้ backend/DBeaver จะต่อฐานข้อมูลไม่ติดเลยแม้ติดตั้งสำเร็จแล้วก็ตาม (ไปเปิดทีหลังได้ผ่าน SQL Server Configuration Manager → SQL Server Network Configuration → Protocols → เปิด TCP/IP → restart service)
  3. รหัสผ่าน sa ต้องผ่านเกณฑ์ความซับซ้อนของ Windows (มีตัวใหญ่ ตัวเล็ก ตัวเลข สัญลักษณ์ อย่างน้อย 8 ตัวอักษร) ไม่งั้นการติดตั้งจะล้มเหลว

หรือติดตั้งผ่าน GUI ธรรมดา (ถ้าไม่ถนัด command line)

รัน bootstrapper แล้วเลือก Custom (ไม่ใช่ Basic) → Database Engine Services อย่างเดียว → Default instance → ในหน้า Database Engine Configuration เลือก Mixed Mode แล้วตั้งรหัส sa → ติดตั้งเสร็จแล้วอย่าลืมไปเปิด TCP/IP ผ่าน SQL Server Configuration Manager เอง (ค่าเริ่มต้นปิดไว้เสมอไม่ว่าติดตั้งวิธีไหน)

ตรวจสอบว่าติดตั้งสำเร็จ

Get-Service MSSQLSERVER   # ต้องเห็น Status = Running
Test-NetConnection -ComputerName localhost -Port 1433

เตรียมฐานข้อมูล

เชื่อมต่อด้วย DBeaver, SSMS หรือ sqlcmd ด้วยบัญชี sa แล้วสร้างฐานข้อมูลเปล่า:

CREATE DATABASE scd_panda;

สร้างตารางทั้งหมด

สลับไปใช้ database scd_panda แล้วรันไฟล์ sql/001_create_schema.sql ที่มากับ repo นี้ (สร้างอัตโนมัติจาก schema-manifest.json — ครบทั้ง 29 ตาราง ตรงกับโครงสร้างที่ backend คาดหวังทุกคอลัมน์)

ถ้าฐานข้อมูลปลายทางมีตาราง scd_panda อยู่แล้ว (เช่น มีคนสร้าง schema ให้ตรงกับ Postgres ไว้ล่วงหน้า) ข้ามขั้นตอนนี้ได้เลย แต่ต้องตรวจสอบว่าคอลัมน์ตรงกับ src/schema-manifest.json ในโค้ดจริง ๆ ก่อน

สร้างบัญชีเฉพาะสำหรับแอป (แนะนำสำหรับใช้งานจริง)

แทนการให้ backend ใช้ sa ตรง ๆ:

USE scd_panda;
CREATE LOGIN scd_panda_app WITH PASSWORD = 'ตั้งรหัสผ่านที่นี่';
CREATE USER scd_panda_app FOR LOGIN scd_panda_app;
ALTER ROLE db_owner ADD MEMBER scd_panda_app;
ถ้าข้ามขั้นตอนสร้างบัญชีเฉพาะไปก่อน ใช้ sa ไปพลาง ๆ ก็ได้ แต่ควรกลับมาทำก่อนใช้งานจริงกับข้อมูลลูกค้า

ตั้งค่า Backend (ไฟล์ .env)

cd backend-sqlserver-scd-panda
cp .env.example .env

แก้ค่าในไฟล์ .env ให้ตรงกับเครื่อง/เซิร์ฟเวอร์จริง:

ตัวแปรคำอธิบาย
MSSQL_HOST / MSSQL_PORT / MSSQL_DATABASEค่าเชื่อมต่อฐานข้อมูลตามที่สร้างไว้ในขั้นตอนที่ 4 (พอร์ตเริ่มต้น 1433)
MSSQL_USER / MSSQL_PASSWORDบัญชีที่สร้างไว้ (scd_panda_app หรือ sa)
MSSQL_ENCRYPTtrue เฉพาะกรณีต่อ Azure SQL หรือเซิร์ฟเวอร์ที่มี TLS certificate จริง ปกติตั้งเป็น false
MSSQL_TRUST_SERVER_CERTIFICATEtrue จนกว่าเซิร์ฟเวอร์จะมี certificate ที่ลงนามจริง
JWT_SECRETข้อความลับใช้เซ็นรหัสเข้าสู่ระบบ ต้องตั้งใหม่ทุกครั้งที่ติดตั้งระบบใหม่ สร้างค่าสุ่มปลอดภัยด้วย openssl rand -hex 32
PORTพอร์ตที่ backend จะรัน (ค่าเริ่มต้น 4001 — ตั้งใจให้ต่างจากรุ่น Postgres ที่ใช้ 4000 เผื่อรันคู่กันบนเครื่องเดียว)
CORS_ORIGINโดเมนของ frontend จริงที่อนุญาตให้เรียก API นี้ (คั่นด้วยจุลภาคถ้ามีหลายโดเมน)

Bun โหลดไฟล์ .env ให้อัตโนมัติ ไม่ต้องติดตั้งแพ็กเกจ dotenv เพิ่ม จากนั้นติดตั้งแพ็กเกจ:

bun install
6

นำเข้าข้อมูลเริ่มต้น

ฐานข้อมูลที่เพิ่งสร้างยังว่างเปล่า (แค่มีตาราง ไม่มีข้อมูล) ต้องมีไฟล์ข้อมูลตามที่ระบุไว้ในขั้นตอนที่ 0 (.bak หรือ Firebase export) อยู่ในมือก่อน แล้วเลือกวิธีนำเข้าให้ตรงกับไฟล์ที่มี:

กรณี A — มีไฟล์สำรองข้อมูล (.bak) จากระบบ SQL Server ที่ใช้งานอยู่แล้ว แนะนำ

ใช้ตอนย้ายเครื่อง/ย้ายเซิร์ฟเวอร์ของระบบที่มีข้อมูลอยู่แล้ว เปิด DBeaver/SSMS แล้ว restore ไฟล์ .bak เข้าฐานข้อมูล scd_panda ที่สร้างไว้ในขั้นตอนที่ 4 โดยตรง (เมนู Restore Database) หรือใช้ T-SQL:

RESTORE DATABASE scd_panda FROM DISK = 'C:\path\to\backup-file.bak' WITH REPLACE;
อย่าลืมคัดลอกไฟล์ src/schema-manifest.json มาจากระบบต้นทางด้วยเสมอ — backend จะไม่รู้จักตาราง/คอลัมน์ที่เพิ่ง restore ถ้าไฟล์นี้ไม่ตรงกับโครงสร้างจริงในฐานข้อมูล

กรณี B — เริ่มจากศูนย์ด้วยไฟล์ Firebase export ล่าสุด แนะนำ

ใช้ตอนตั้งระบบใหม่ครั้งแรกโดยไม่มีไฟล์สำรอง หน้าเว็บต้องล็อกอินก่อนถึงจะเห็นปุ่มนำเข้าข้อมูล แต่ฐานข้อมูลเปล่ายังไม่มีบัญชีให้ล็อกอิน (ไก่กับไข่) วิธีที่ง่ายที่สุดคือสร้างบัญชีผู้ดูแลระบบชั่วคราวด้วย SQL สั้น ๆ ก่อน แล้วนำเข้าข้อมูลจริงผ่านปุ่มในหน้าเว็บตามปกติ:

รันไฟล์ sql/002_seed_test_login.sql ที่มากับ repo นี้ (ผ่าน DBeaver/SSMS ต่อฐานข้อมูล scd_panda) จะได้บัญชีชั่วคราว 1 บัญชี: user testadmin / password test1234 จากนั้น:

  1. รันเซิร์ฟเวอร์ (ขั้นตอนที่ 7) แล้วล็อกอินด้วยบัญชีชั่วคราวข้างต้นผ่านหน้าเว็บ
  2. กดปุ่ม "นำเข้าข้อมูล JSON (ทับข้อมูลเดิมทั้งหมด)" แล้วเลือกไฟล์ Firebase export ล่าสุด (Firebase Console → Realtime Database → ปุ่มจุดสามจุด ⋮ → Export JSON) — ปุ่มนี้ลบและสร้างทุกตารางใหม่ทั้งหมด บัญชีชั่วคราวจึงหายไปเองพร้อมขั้นตอนนี้ และรหัสผ่านบัญชีจริงทุกบัญชีจะถูกเข้ารหัสให้อัตโนมัติ
  3. ล็อกเอาต์ แล้วล็อกอินใหม่ด้วยบัญชีผู้ดูแลระบบจริงจากระบบเดิม
ต้องใช้ปุ่ม "ทับข้อมูลเดิมทั้งหมด" ไม่ใช่ "เพิ่มข้อมูลใหม่ (ไม่ลบของเดิม)" — ถ้าใช้ปุ่มเพิ่มข้อมูลแทน บัญชีชั่วคราวจะไม่ถูกลบอัตโนมัติ ต้องเข้าไปลบเองทีหลังจากหน้าจัดการพนักงาน

กรณี C — bootstrap ผ่าน command line ล้วน (ไม่อยากเปิดเบราว์เซอร์เลย)

ทำสิ่งเดียวกับกรณี B โดยไม่ต้องล็อกอินผ่านหน้าเว็บเลย เรียก endpoint /api/bootstrap-import ตรง ๆ (รหัสเริ่มต้น ChangeMe123! — เปลี่ยนได้จากหน้า Setting หลังมีบัญชีจริงแล้ว):

bun -e "
const data = JSON.parse(require('fs').readFileSync('firebase-export.json', 'utf8'));
const res = await fetch('http://localhost:4001/api/bootstrap-import', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ code: 'ChangeMe123!', data }),
});
console.log(await res.json());
"
ผลลัพธ์การนำเข้าปกติควรขึ้น "success" อย่างเดียว ไม่มีคำเตือน ระบบแก้ปัญหาที่พบได้บ่อยในไฟล์ Firebase export ให้อัตโนมัติแล้ว: id ที่ชนกันในตารางเดียวกันจะถูกสลับให้ไม่ซ้ำกันเอง (ไม่ใช่แค่เตือน), ค่า placeholder ของแอปเดิมอย่าง "0:ไม่มี" จะไม่ถูกนับเป็นข้อมูลเชื่อมไม่สำเร็จ และตาราง company_history/customer (ไม่ได้มาจาก Firebase) จะถูกสร้าง/อัปเดตให้เองทุกครั้ง — ถ้าเจอคำเตือนซ้ำ ๆ ทุกครั้งที่ import แปลว่าเป็นปัญหาข้อมูลจริงที่ต้องตรวจสอบที่ต้นทาง (Firebase) ไม่ใช่เรื่องปกติที่ต้องเพิกเฉย ไฟล์ขนาดใหญ่ (หลายสิบ MB) อาจใช้เวลานำเข้าหลายนาที ให้รอจนกว่า request จะตอบกลับ

cd frontend-scd-panda

ค่านี้ถูกฝังเข้าไปในไฟล์ที่ build ออกมาแบบถาวร ถ้าเปลี่ยนที่อยู่ backend ภายหลัง ต้อง build ใหม่ทุกครั้ง แก้แค่ .env.local เฉย ๆ โดยไม่ build ใหม่จะไม่มีผลอะไรเลย

อย่าลืมตั้งค่า CORS_ORIGIN ฝั่ง backend (ขั้นตอนที่ 5) ให้ตรงกับโดเมนที่จะ deploy หน้าเว็บนี้ด้วย ไม่งั้นเบราว์เซอร์จะบล็อกการเรียก API ทั้งหมด

Build เว็บสำหรับใช้งานจริง:

npm run build

จะได้โฟลเดอร์ build/ ที่มีไฟล์ static ล้วน พร้อมเอาไปวางบนเว็บเซิร์ฟเวอร์ใดก็ได้

9

Deploy โฟลเดอร์ build/

วิธีที่ 1 — IIS แนะนำสำหรับเครื่อง Windows ที่มีอยู่แล้ว

เครื่องนี้เป็น Windows อยู่แล้วจากการติดตั้ง SQL Server จึงสะดวกใช้ IIS ที่มากับ Windows เอง: เปิด "Turn Windows features on or off" → เปิด Internet Information Services → สร้าง Site ใหม่ชี้ไปที่โฟลเดอร์ build/ → ติดตั้ง URL Rewrite module แล้วเพิ่มกฎ rewrite ทุก path ที่ไม่ตรงกับไฟล์จริงไปที่ index.html (จำเป็นเพราะเป็น SPA)

วิธีที่ 2 — nginx/Apache

คัดลอกเนื้อหาในโฟลเดอร์ build/ ไปไว้ในโฟลเดอร์ที่เว็บเซิร์ฟเวอร์ชี้ถึง แล้วตั้งค่า rewrite แบบเดียวกัน ตัวอย่าง nginx:

server {
  listen 80;
  server_name app.โดเมนลูกค้า.com;
  root C:/inetpub/wwwroot/scd-panda;
  index index.html;

  location / {
    try_files $uri /index.html;
  }
}

ไม่ว่าใช้วิธีไหน แนะนำให้ตั้ง HTTPS (เช่นผ่าน reverse proxy หรือ certificate ใน IIS) แทนการเปิด HTTP เปล่า ๆ ออกอินเทอร์เน็ต

ดูแลรักษาต่อเนื่องหลังส่งมอบ

  • สำรองข้อมูลอัตโนมัติ — ระบบสำรองข้อมูลให้เองทุกวันตี 1 (เก็บย้อนหลัง 30 วัน) ด้วยคำสั่ง BACKUP DATABASE ของ SQL Server เอง ได้ไฟล์ .bak ทำงานทันทีที่เซิร์ฟเวอร์ backend รันอยู่ ไม่ต้องตั้งค่าเพิ่ม — แค่ต้องแน่ใจว่า SQL Server service account เขียนไฟล์ที่โฟลเดอร์ backups/ ได้จริง (ทดสอบครั้งแรกด้วยการกดสำรองข้อมูลเองจากหน้าเว็บ)
  • อัปเดตโค้ดในอนาคต — git pull ที่ repo ที่เกี่ยวข้อง แล้วรัน bun install/npm install ใหม่ถ้ามีแพ็กเกจเพิ่ม จากนั้น restart backend หรือ build+deploy frontend ใหม่แล้วแต่ฝั่งที่แก้
  • ตรวจสอบระบบยังทำงานปกติ — curl <backend-url>/health ควรตอบ {"ok":true} เสมอ
  • Restore จากไฟล์สำรอง — ผ่าน DBeaver/SSMS เมนู Restore Database หรือคำสั่ง RESTORE DATABASE scd_panda FROM DISK = '...' WITH REPLACE;
